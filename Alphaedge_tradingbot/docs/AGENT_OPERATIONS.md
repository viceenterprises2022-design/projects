# AlphaEdge — Operational agent layer

**Status:** design only. **Post-launch**, none of it on the day-1..10 critical path (§0.2).
**Date:** 2026-07-28
**Companion to:** [PRODUCTION_DESIGN.md](PRODUCTION_DESIGN.md) §3, which defines A1–A6 and the rules
every agent here inherits.

Covers the five operational capabilities requested on 2026-07-28: log management, user account
management, trade analytics, announcement blogs, and outbound client updates.

---

## 0. Two things to settle before the designs

### 0.1 Three of the five are extensions, not new agents

An agent layer rots when every new capability becomes a new agent. Nine agents with overlapping
scopes are worse than six with clean ones — they duplicate context, disagree with each other, and
nobody can say which one owns a decision. Honest mapping of the five asks:

| Ask | Verdict | Where it lands |
|---|---|---|
| Log management | **Extend A3** + real log infrastructure | §1 — A3 gains a proactive mode; most of the work is not the agent |
| User account management | **Extend A5** | §2 — A5 grows from onboarding-only to full account lifecycle |
| Analytics of trades | **No new agent.** Build the compute layer | §3 — a deterministic attribution layer that A2 and A4 both read |
| Announcement blogs | **New: A7** | §4 — different audience (public), different risk (marketing claims) |
| Regular client updates | **New: A8** | §5 — outbound messaging is genuinely new infrastructure |

Net: A1–A6 stay six, two are rescoped, two new agents. **Eight total.**

> **Revision 2026-08-01 (HLD decision 19):** operations are automation-first. Deterministic policy
> replaces the human click for provisioning and low-risk lifecycle transitions; ladder-eligible
> workflows (A7 changelog, A8 routine sends, A5′ dormancy/reactivation) graduate to auto-execution
> after 10 consecutive unchanged approvals, with sampled review and per-workflow kill switches
> (LLD §22.5). The "permanently human" floor is unchanged: owner halt/unlock, public blog, suspension
> for cause, closure, money path, strategy deployment. A5′'s onboarding gate is retired — the
> §22.4 eligibility policy auto-activates; A5′ reviews exceptions and anomalies instead.

The one that most wants to be an agent and should not be is trade analytics. "Ask the AI about your
trades" is a demo; a correct attribution table is a product. Build the table, and A2 and A4 both get
better for free — §3.

### 0.2 None of this is in the ten days

Day 10 is company money live (design doc §7). Everything in this document is post-launch. Two
carve-outs, because they are cheap and expensive to retrofit:

- **The structured log schema and correlation ID (§1.1)** must be right from the first line of
  `Alphaedge_live/`. Retrofitting correlation IDs through an existing codebase is miserable, and
  without them A3's proactive mode has nothing to work with. Cost now: about two hours.
- **The `outbound_messages` table and opt-out flags (§5.1)** should exist in the day-5 schema even
  though nothing writes to them until later. Adding a table is free; backfilling consent is not.

Everything else waits until after the soak.

### 0.3 The publication gate — shared by A7 and A8

Any agent-authored text that reaches a human **outside the company** passes four checks in order.
This is one component, used by both new agents, and it is where the compliance surface concentrates:

1. **Claims verification.** Every numeric claim in the draft must be traceable to a query the
   verifier can re-run. The agent emits text *and* a claims manifest —
   `{ "claim": "142 trades last month", "query_id": "trades_count_period", "params": {...} }`. The
   verifier runs each query and compares. Mismatch or unbacked number ⇒ the draft is rejected back
   to the agent, not to the human. Models are good at prose and bad at arithmetic; this makes that
   asymmetry structural instead of hoping.
2. **Prohibited-content check.** A deterministic classifier pass for: forward-looking statements
   ("expect", "should return", "projected"), guarantees, personalised advice, competitor
   comparisons, and any reference to another client's data. Hit ⇒ rejected.
3. **Approval.** Public content (A7) requires an owner click, permanently. Per-account content (A8)
   requires the message to be template-bound — the agent fills named slots in an approved template
   and cannot alter the surrounding text.
4. **Immutable record.** What was sent, to whom, when, generated by which `agent_run`, approved by
   which user. Stored in `outbound_messages`, never deleted.

The gate is deterministic code. It is not a prompt instruction, and no agent can skip it, because
neither A7 nor A8 has a tool that publishes or sends — they only have tools that *submit to the
gate*.

## 1. Log management — A3 rescoped, plus the substrate

### 1.1 The substrate matters more than the agent

An agent reading unstructured logs is a party trick. An agent reading well-structured logs is an
on-call engineer. The design work is mostly here.

**Logs are not the ledger.** Keep the distinction absolute:

| | Ledger | Logs |
|---|---|---|
| Contains | Trade facts: intents, orders, fills, risk events, regime transitions | Operational telemetry: HTTP retries, latencies, cache misses, task lifecycle |
| Store | Postgres, hash-chained, immutable | External sink |
| Retention | Forever | Tiered (below) |
| If lost | We cannot prove what we did — existential | We debug more slowly |

A fill lives in the ledger. The three venue retries that preceded it live in logs. Never write trade
facts only to logs, and never bloat the ledger with telemetry.

**Every log line is structured JSON** carrying:

```
correlation_id   — the intent_id where one exists; otherwise the Trigger.dev run id
account_id       — or null for desk-level events
component        — strategy | risk | execution | reconcile | agent | api | auth
severity         — debug | info | warn | error | fatal
event            — a stable enum, never an interpolated sentence
```

`event` as a stable enum is what makes anomaly detection possible: you cannot count occurrences of
`Failed to place order for user 8a3f...` but you can count `execution.order_rejected`. Interpolated
values go in fields, never in the event name.

**Correlation ID threading is the single highest-value line of this section.** One `intent_id`
should let you pull the strategy decision, the risk verdict, every venue call, the fill, the ledger
append, and the reconciliation that confirmed it — in one query, across five components. This is
also exactly what A4 needs to answer "why did this trade happen?" for a client.

**Redaction happens at the logger, not the sink.** An allowlist of loggable fields; request and
response bodies are never logged wholesale. Signing keys, API tokens and session cookies are
unloggable by construction — the logger rejects them. Emails are hashed. A redaction bug discovered
at the sink means the secret already left the building.

**Retention tiers**, driven by §6.1 of the design doc:

| Tier | Window | Contents |
|---|---|---|
| Hot, searchable | 30 days | Everything |
| Warm | 13 months | `warn` and above, plus everything carrying a `correlation_id` |
| Cold, archival | 7 years | Anything whose correlation ID resolves to a fill |

**Sink:** Vercel's log retention is ephemeral and Trigger.dev's run logs are scoped to runs — neither
survives as a queryable operational record. We need a real sink; Axiom is the cheapest that handles
this volume with structured search. Decision deferred, but not past the first live account.

### 1.2 A3′ — Ops & Observability (rescoped)

| | |
|---|---|
| **Trigger** | *Reactive* (unchanged): reconciliation diff, execution failure, feed outage, error burst. **New — proactive:** daily sweep at 06:00 UTC |
| **Reads** | The incident and surrounding state (reactive); 24h of aggregated log statistics vs 7-day baselines (proactive); its own last 20 scored runs |
| **Tools** | `get_incident`, `get_engine_state`, `search_logs`, `get_error_signatures`, `get_component_health`, `search_runbooks` |
| **Writes** | Incident classification + drafted operator alert (reactive); a daily ops digest draft (proactive) |
| **Authority** | **Read and notify only**, unchanged. No tool in its surface mutates anything |
| **Model** | `claude-opus-5`, `effort: "medium"` |

The proactive sweep looks for four things, each computed deterministically and handed to the model
as a table:

- **Error-rate deltas** per `component` × `event` against the 7-day baseline.
- **New error signatures** — an `event` enum seen for the first time ever, or the first time in 30
  days. New failure modes matter more than familiar ones.
- **Latency drift** on venue calls, p50 and p99. Rising p99 on order placement is the leading
  indicator of fill quality decay, and it will show up here weeks before it shows up in A2's
  execution-quality numbers.
- **Silent failures.** The most valuable one and the reason the proactive mode exists at all: a
  component whose log volume dropped to zero. A crashed cron produces *no* errors — it produces
  nothing, and every purely reactive monitoring system is blind to it by construction. Expected
  heartbeat events per component per hour are declared; a shortfall raises.

Both modes still only notify. A3′ proposes a runbook step; a human runs it.

## 2. User account management — A5 rescoped

### 2.1 The lifecycle

```
pending ──▶ approved ──▶ funded ──▶ active ──┬──▶ dormant ──▶ active
                                             ├──▶ suspended ──▶ active
                                             └──▶ closing ──▶ closed
```

Every transition needs a decision, a reason, and an audit record. Today only the first one exists,
and its reason field is empty.

### 2.2 A5′ — Account Lifecycle Reviewer (rescoped)

| | |
|---|---|
| **Trigger** | New onboarding profile (unchanged); daily lifecycle sweep; event-driven on credential or reconciliation signals |
| **Reads** | Onboarding profiles, account states, credential metadata (never the credential), fill recency, reconciliation history, open incidents from A3′ |
| **Tools** | `get_onboarding_profile`, `get_account_state`, `get_credential_health`, `get_account_activity`, `draft_recommendation` |
| **Writes** | A recommendation packet on the `/admin/users` queue: proposed transition, evidence, and drafted reason text |
| **Authority** | **Recommend only, permanently.** No transition executes without a human click. Role, funding, and suspension changes stay human actions with no exception path |
| **Model** | `claude-opus-5`, `effort: "low"` |

Five jobs beyond onboarding:

- **Credential health.** API wallet approaching expiry, revoked upstream, or failing auth. Detected
  from metadata and auth-failure events — the agent never touches key material. Recommends a
  rotation prompt to the client and, if the credential is dead, a pause.
- **Dormancy.** An account armed and funded but with no fills in 30 days is an unattended risk
  surface: the client may have forgotten it exists while it still trades their money. Recommend
  pause + re-confirmation.
- **Suspension.** Fed by A3′: repeated reconciliation breaks or persistent execution failure on one
  account. Recommends suspension with the incident trail attached.
- **Reactivation.** The symmetric case, and the one systems always forget — a dormant or suspended
  account whose blocking condition has cleared. Without this, accounts silently rot in a paused
  state and the client's money sits idle.
- **Offboarding.** A checklist, not a judgement: positions flat, orders cancelled, API wallet
  revoked, final statement generated, retention obligations recorded. The agent verifies each item
  and blocks the close until all pass.

**The drafted reason text is the underrated output.** Audit trails fail not because the transition
is unrecorded but because the *why* is a blank field or "approved". A5′ writes a specific,
evidence-cited reason for every recommendation; when the owner clicks accept, that text becomes the
audit record. Given §6.1's retention requirements, an audit trail that explains itself is worth
considerably more than one that merely exists.

## 3. Trade analytics — build the compute, not an agent

### 3.1 Why no agent here

An agent that queries trades and narrates them is impressive in a demo and unreliable as a product:
non-reproducible numbers, latency on every view, cost per question, and no way to put it on a
dashboard. What clients and the desk both need is **a correct attribution table**. Build that, and
A2 (§design doc) interprets it daily while A4 explains it per-client on demand. Both agents get
better; neither needs new authority.

### 3.2 The attribution decomposition

For any account over any window, gross-to-net decomposed into terms that sum exactly:

```
  signal P&L          price movement captured, at decision prices
− execution cost      ├─ fees        (maker/taker, per §6.3)
                      ├─ funding     (8h settlements crossed)
                      └─ slippage    (fill price vs decision price)
± sizing effect       the account's risk multiplier vs the 1× baseline
= net P&L
```

Every term is a materialised view keyed on `(account_id, period)`, recomputed on fill. No model is
involved in producing any number in this table.

### 3.3 The counterfactual — the part that is genuinely differentiated

Alongside realised P&L, compute what would have happened **without the risk controls**: the trades
the regime lock skipped, the entries the funding-crossing check rejected, the size the correlation
cap removed. Each control gets a running "what it cost you / what it saved you" line.

This is uncomfortable and that is the point. Some months the regime guard will have cost money, and
the honest number will say so. A desk that publishes that number when it is negative is the only
kind whose positive numbers mean anything — and it converts risk management from an invisible tax
into a visible, measurable product feature. It also gives A2 a hard signal for tuning: a control
that has cost money for six consecutive months is a control to re-examine, and without the
counterfactual nobody would ever know.

### 3.4 What this feeds

- **The client analytics page** — attribution table, equity curve, per-control counterfactual.
- **A2's daily review** — drift detection now runs against attribution terms, so it can say
  *which* term decayed: signal, execution, or sizing. "The edge is gone" and "our slippage doubled"
  need very different responses, and only the decomposition tells them apart.
- **A4's per-trade explanations and weekly briefs** — same numbers, client-scoped.
- **A6's re-validation** — live attribution vs backtest attribution, term by term.

## 4. A7 — Content & Announcements (new)

| | |
|---|---|
| **Trigger** | Owner-initiated; or on a tagged release |
| **Reads** | Git log and release diff, changelog entries, A2 daily reviews, resolved incidents, existing published posts (for voice and to avoid repetition) |
| **Tools** | `get_release_diff`, `get_changelog_entries`, `get_published_posts`, `get_desk_statistics`, `submit_draft_to_gate` |
| **Writes** | A draft post. Nothing else |
| **Authority** | **Draft only.** No publish tool exists. Owner approval is permanent and unconditional, and the §0.3 gate runs before the owner ever sees the draft |
| **Model** | `claude-opus-5`, `effort: "medium"` |

Two content types, and the distinction is load-bearing:

- **Changelog entries** — factual, internal-facing-ish, derived from the release diff. Low risk. The
  demo already has the approval-gate pattern for these (commit `0b59671`); port it.
- **Public blog posts** — marketing content about a financial product, read by retail prospects.
  High risk, and the risk is not technical. This is where a plausible sentence like "the desk
  returned 4% last month" becomes a performance representation.

**Prohibited by the gate, not by prompt:** performance claims without the standard disclosure block,
any forward-looking statement, guarantees or implied guarantees, competitor comparisons, and any
reference to an individual client or their data. Every number in a public post resolves through the
claims verifier to a query against our own database — if the desk statistic cannot be produced by a
query, it cannot appear in a post.

Worth stating plainly: A7 is the lowest-value agent in the system and carries the highest
per-word risk. It is here because you asked and because the changelog half is genuinely useful.
Build the changelog half first, and treat public marketing copy as a thing the gate permits rather
than a thing the agent owns.

## 5. A8 — Client Communications (new)

### 5.1 Delivery substrate

| | |
|---|---|
| `outbound_messages` | Every message: account, channel, template id, rendered body, generating `agent_run`, approver, sent_at, delivery status |
| `communication_preferences` | Per account: channel opt-ins, frequency cap, timezone, and a global opt-out that the *delivery layer* enforces — not the agent |
| Channels | In-app first (no deliverability or consent surface), then email opt-in, then Telegram opt-in |

Opt-out is enforced at the delivery layer deliberately. An agent that "knows" not to message someone
is one bad context away from messaging them; a delivery layer that refuses is not.

### 5.2 A8 — the agent

| | |
|---|---|
| **Trigger** | Scheduled (weekly brief, monthly statement); event-driven (incident affecting the account, material change) |
| **Reads** | The target account's own data only — attribution (§3), fills, locks honoured, incidents affecting it |
| **Tools** | `get_account_attribution`, `get_account_events`, `render_template`, `submit_to_gate` |
| **Writes** | A queued outbound message. Never a sent one |
| **Authority** | **Template-bound composition only.** Fills named slots in an approved template; cannot alter surrounding text, cannot compose free-form, cannot send |
| **Model** | `claude-opus-5`, `effort: "low"` |

Four message types:

| Type | Cadence | Content |
|---|---|---|
| Weekly brief | Weekly | What the desk did, cost decomposition, locks honoured, equity curve. (This is A4's weekly brief from design doc §3.2 — A8 owns delivery, A4 owns content) |
| Monthly statement | Monthly | Full attribution table, counterfactual, fee and funding totals |
| Incident notice | Event | Their account was halted / a reconciliation break affected them / trading paused |
| Material change | Event | Strategy parameter change, fee change, terms change — owner-triggered, never agent-triggered |

**Controls that are structural, not advisory:**

- **Rate limit**: a hard per-account weekly cap in the delivery layer. Incident notices may exceed
  it; nothing else can.
- **Quiet hours** by account timezone for non-incident messages.
- **No advice, no forecasts** — enforced by the §0.3 prohibited-content check, same as A7.
- **Human send, initially.** A8 queues; the owner reviews and releases. Auto-send unlocks only for
  the template-bound routine briefs, only after a review period where the owner has approved a run
  of them unchanged. Incident and material-change notices stay human-released permanently.

The failure mode to design against is not a badly-worded email. It is a loop: an incident triggers
notices to 400 accounts, the sends fail, the retry fires, and clients receive the same alarming
message eleven times at 3am. Idempotency on `(account_id, event_id, template_id)` and a global
per-hour send ceiling with an owner alert on breach.

## 6. Revised agent roster and cost

| Agent | Scope | Authority | Effort | Status |
|---|---|---|---|---|
| A1 Regime | Regime lock/release | Auto, layer-bounded | high | Day 8 |
| A2 Post-Trade | Drift + execution quality | Draft + `drift_warning` | xhigh | Post-launch |
| A3′ Ops | Incidents + proactive log sweep | Notify only | medium | Post-launch |
| A4 Concierge | Client explanation, brief content | Read-only + brief draft | low | Post-launch |
| A5′ Account Lifecycle | Full lifecycle recommendations | Recommend only | low | Post-launch |
| A6 Strategy R&D | Spec + backtest | Cannot deploy | xhigh | Parallel, anytime |
| A7 Content | Changelog + blog drafts | Draft only, owner publishes | medium | Post-launch, last |
| A8 Client Comms | Outbound delivery | Queue only, human sends | low | Post-launch |

Incremental cost over the ~$260/month baseline in design doc §3.6:

| Agent | Runs/day | ~Input | ~Output | $/run | $/month |
|---|---:|---:|---:|---:|---:|
| A3′ proactive sweep | 1 | 40K | 5K | $0.33 | ~$10 |
| A5′ lifecycle sweep | 1 | 15K | 3K | $0.15 | ~$5 |
| A7 Content | ~0.3 | 30K | 6K | $0.30 | ~$3 |
| A8 Client Comms | ~15 (at 100 accounts) | 6K (5K cached) | 1.5K | $0.043 | ~$19 |
| | | | | **Added** | **~$37/mo** |

Cheap, because the expensive parts are deterministic. A8 scales linearly with account count —
at 1,000 accounts it is roughly $190/month, still trivial against the value of every client
getting a personalised statement.

**Note both new agents are `low`/`medium` effort.** They are not doing hard reasoning; they are
rendering verified facts into prose inside a template. The hard reasoning lives in A2 and A6, and
the hard *correctness* lives in the deterministic layers underneath all of them.

## 7. What to build in what order

1. **Now, inside the ten days:** structured log schema + correlation ID (§1.1), and the
   `outbound_messages` / `communication_preferences` tables (§5.1). Two hours; retrofitting is days.
2. **First week post-launch:** the attribution layer (§3). Everything else reads it, and it is
   deterministic code with no agent risk.
3. **Then:** A3′ proactive mode — you will want it the first time a cron dies silently.
4. **Then:** A5′ lifecycle, once there are enough accounts for the sweep to matter.
5. **Then:** the publication gate (§0.3), followed by A8 in queue-only mode.
6. **Last:** A7, changelog half first, public blog only once the gate has proven itself on A8.

The ordering principle: every agent that talks to a client ships after the gate that checks it, and
every agent ships after the deterministic layer it reads from.
